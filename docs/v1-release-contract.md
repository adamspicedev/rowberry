# V1 release contract

Planning baseline established 23 October 2026 following acceptance of the [council roadmap](roadmap-v1.md). This contract defines completion criteria; it is not a release sign-off. Track execution in the [to-do list](v1-todo.md) and results in the [evidence register](qa/v1-evidence-register.md). The [release checklist](release-checklist.md) remains authoritative if a requirement here is less detailed.

## Scope

V1 is a free, GPL-3.0-only, local PostgreSQL workspace for macOS Apple silicon (arm64). Users must be able to connect securely, inspect tables and JSON, run SQL, deliberately edit eligible values, recover work and manually update the app. No account or hosted service is required.

On 23 October 2026 the maintainer approved Apple silicon-only v1 because Intel test hardware is outside the current budget. Intel native qualification and supported downloads are deferred; Intel build checks are paused. The current macOS target and PostgreSQL coverage are defined in [supported platforms](supported-platforms.md); verify the final minimum OS against the shipped Electron version. PostgreSQL 14/18 full workflow coverage and 15–17 connection/authentication compatibility coverage must be distinguished in release claims.

Intel Macs, Windows/Linux, other database engines, bulk import/COPY, multi-statement scripts, editable arbitrary query results, visual schema administration, automatic updating and hosted collaboration remain deferred. V1-06 must decide result export before preview acceptance. Read-only query results do not imply a read-only connection: SQL uses the database role's permissions.

## Acceptance tasks

Use disposable databases and OS test accounts, never production data. Identify the package and fixture before each run. A pass requires the observable outcome plus retained evidence; a test name or an unchecked checklist is insufficient. Native tasks must run on each advertised architecture. Automated tests supplement human workflow evidence.

V1-03 starts with three unfamiliar participants as a practical discovery target, not a statistical quality claim. Record coaching separately: assisted completion cannot prove uncoached usability. V1-05 must record hardware, workloads and numeric performance budgets before measuring qualification; historic timing samples are not those budgets.

## Blocking conditions and sign-off

Data loss, wrong-target writes, silent conflicts, credential exposure, false save success, an unusable core task or a failed required native/distribution check blocks release. Missing required evidence also blocks release; it does not establish a code defect. Unresolved failures need a fix and relevant requalification, or an explicit recorded scope change where permissible.

Each final candidate record must identify full source revision, version, OS/architecture, final installer and app archive hashes, durable artifact identifiers, signing status, fixture, tester/date, procedure, actual result and retained evidence. Record CI against its own source revision. If source or package changes, assess and repeat affected qualification; never transfer historical results silently.

QA records outcomes, engineering resolves findings, product assesses observed usability and scope, and the maintainer accepts each advertised target and separately authorizes publication. Planning approval does not grant publication approval. The [evidence register](qa/v1-evidence-register.md) must link each required task to exact-candidate evidence before final sign-off.
