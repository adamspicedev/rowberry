# macOS packaged-workspace QA — 21 October 2026

## Scope and build

Tested Rowberry 0.1.0 at commit `beae84dcf6d436b6173a70d1af0cc892ad3b5cf3` on macOS 27.2 (26B5112a), Apple Silicon arm64. The checkout was clean when built. Tooling: Bun 1.4.3, Node 20.20.2, Electron 44.9.0.

Built an unsigned DMG with `bun run package --mac --arm64 -c.directories.output=/tmp/rowberry-qa-20261021/release`. The configured targets also produced an Intel DMG; it was not exercised in this pass. Mounted the arm64 DMG read-only, copied its application to an isolated installation directory, detached the image, and launched that copy with a new user-data directory.

- DMG SHA-256: `b10d08c59169a3fbb887a65ef2e7ce022e90caeda2499826e1fabbcd64de043f`
- Installed `app.asar` SHA-256: `4e9a9420fe1fd2389c095ab4eda1d677679ed0133536ae40940e982ebde0ada6`
- Local artifacts and driver: `/tmp/rowberry-qa-20261021/` (temporary, not required to read this report).

This was desktop automation against the production executable on the existing macOS account, with a fresh application profile. It was not a fresh OS account, Finder drag-and-drop installation into `/Applications`, upgrade, signed distribution, or Gatekeeper qualification. Native quit-confirmation responses were selected by the driver; other workflow operations used renderer controls. Read-only bridge calls confirmed durable draft state. After the Mac was unlocked, native accessibility controls were used to select and delete the disposable connection, quit, and inspect the restarted application.

The automated journey reached all connection, query, restart, and recovery assertions before a deletion-driver timeout caused by not selecting the profile. The native follow-up completed deletion and verified persistence after restart. Visual inspection showed a settled empty workspace with no loading or recovery screen. Earlier driver attempts also needed normal select-all/typing for Monaco, and handling of a dialog event during application shutdown; these were not counted as application failures. No loading/recovery loop was reproduced in the completed journey.

The two existing credential tests passed against the installed binary with `DBAPP_NATIVE_CREDENTIAL_TEST=1`. The separate QA connection's Keychain entry was subsequently removed through the packaged native adapter, with absence verified. That first UI deletion verified profile removal with an already-absent credential. A subsequent native UI pass created a separate disposable profile, `QA live credential deletion`, with password storage enabled. A read-only check through the packaged native Keychain adapter confirmed the exact fixture password existed before deletion. Deleting that profile through the UI removed both its SQLite record and Keychain entry. After quitting and restarting the installed app, the UI still showed zero saved connections and a second read-only check confirmed both remained absent. This closes the live-credential UI deletion gap; no database connection was needed for this storage lifecycle check. All disposable PostgreSQL fixtures were cleaned up. The isolated profile remains in the temporary evidence directory; the user's application profile was not used.

## Follow-up findings

1. **Recovery warning — fixed in this change:** recovered copies previously shared the active-editor dirty marker, so reconnecting asked to discard copies it actually retained. Recovery now uses a separate marker: connection/table changes and disconnect ignore detached copies, while closing the app still protects them. The desktop regression verifies a reconnect attempt proceeds without a discard prompt and retains the exact recovered value; the existing close/cancel regression still passes. No recovered data loss was observed. This fix was tested in the rebuilt development executable; the earlier DMG digests above describe the pre-fix package.
2. Fresh-account install, upgrade from an agreed baseline, actual locked-Keychain behavior, signatures/notarization, and Windows/Linux desktop qualification remain open.
